一、三项裁决记录
1.1 灯语 → 降级为可配置选项，不作亮点项。 理由采纳：后续车机会有虚拟或实体智能助手，灯光语言应该是助手的配合通道（助手表情/动作的延伸），不是独立交互亮点。demo 中的处理：呈现形式以「HUD 轻条 + 卡片 + TTS 一句话」为主，灯语进设置项（默认关），演示时口头说明"未来由智能助手承接这个通道"。
1.2 客人模式 → 砍掉。 车机已有类似功能，不是模糊需求的增量，从方案和 storyboard 中移除。隐私相关演示保留硬约束层（记忆授权、注入拦截），不再单独成旅程。
1.3 呈现管家 → 有必要、有冲突、有归属，结论是"窄版进 demo、宽版归语音助手方向"。 完整核实见第二章。

2.2 三个判断
必要性：成立。 五处"主动"没有一个管整车呈现预算——POI 推荐是地图域的、推荐场景是运营的、迎宾是账号域的，各出各的。fable 说的"五个功能各自每周两张卡，用户一周吃十张"不是假设，是现状结构必然。
冲突：与语音助手的机会方向正面重叠。 语音 PRD 已把"舱内外感知+小塔主动推荐"列为差异化机会。如果呈现管家做成座舱级、由场景编排团队主导，等于抢了语音团队认领的方向，跨团队阻力可预期。
归属：宽版归小塔（语音助手），场景编排做消费方和共建方。 建议的划界方式——谁判断时机（呈现管家，宿主小塔）、谁生产内容（各域：场景大脑产编排卡、地图产 POI、账号产迎宾）、谁执行（各域引擎）。本期 demo 做窄版：呈现管家只管场景卡片这一类内容的预算、冷却、形式选择，验证机制；座舱级宽版写进展望，推进方式是和语音团队共建对齐，不是自建。

三、观察入口：不靠语音的主动建议（新方向）
3.1 三入口框架
此前的方案只有两个入口：语音（显式请求直达、弱意图走门控）和场景 app（编排页面+运营推荐场景库）。第三个入口是观察入口——用户什么都没说，系统基于记忆和行为观察主动发起。
关键设计：观察入口和语音弱意图走同一个门控——它们是同一个判断系统（四路信号、三态输出、价值门控、冷却）的两个输入通道。语音弱意图是"用户说出来的需求"，观察入口是"用户没说但反复做出来的需求"。判断逻辑完全复用，架构上只新增输入源，不新增判断系统。
3.2 观察入口的信号源（全部已有，无需新增采集）
场景执行后的手动调整：场景 PRD 已有"动作能力自适应"（执行后 10 分钟监听参数变化）——已有，参数级；
重复操作序列：连续 N 天同一时间同一位置出现同一组手动操作（如每晚到家都手动调暗灯光+放轻音乐）——小塔记忆 PRD 3.2.5.3"操作行为记忆提取"已规划（P2）；
未编排的高频组合：用户多次手动逐项执行一组动作但从未存成场景——从操作日志挖掘；
上下文信号：日历（明天早出发）、电量、天气、位置、成员构成——车身状态服务已有。
3.3 核心机制：从参数自适应到场景级建议
公司已有的"动作能力自适应"是观察入口的种子形态：它监听已存场景执行后的参数调整。观察入口是两级升级：①从"参数级"升到"场景级"——不只是调参，而是发现"你反复手动做一组事"并建议存成场景；②从"场景内闭环"升到"全舱行为流"——不限于已存场景的执行后窗口，覆盖日常操作序列。
机制四步（对齐小米 HyperMind 的"习得→许可→执行"，加我们自己的分寸层）：
模式挖掘（离线、idle-time）：行为流+操作日志→候选模式（组合动作出现≥3 次、时间/位置条件稳定才算）；
建议生成：候选模式+记忆+当前状态→建议卡片（"注意到你到家后常调暗灯光放轻音乐，要存成『到家放松』场景吗？"）；
呈现与确认：走呈现管家，形式按信任分级（见第四章）；
习得沉淀：确认后成为个人场景库成员，进入"动作能力自适应"的持续调参循环。

3.5 学术侧：观察入口不改变已有结论
此前两轮调研的学术框架（PASK 三态决策、ProAct 价值门控）都是"响应式主动"——用户先说话。观察入口引入的是"无语音触发"，判断逻辑不变，新增的只是触发前多了一层"模式显著性"门槛（ProAct 的 idle-time 计算正好用在这里：模式挖掘放在系统空闲时做，零交互成本）。价值门控在观察入口更重要——用户没说话意味着没有明确的意愿信号，打扰的成本更高，呈现预算应该卡得更严（建议：观察入口的每日预算独立于语音入口且更低，比如 2 天 1 张）。
四、超越卡片：呈现形式矩阵
回应"除了弹卡片还有什么"——卡片只是呈现形式之一，且不是最高级的。按信任等级 × 风险等级分级呈现：
| 信任阶段 | 低风险动作（灯光/媒体/空调） | 中风险（座椅/悬架/导航改道） | 高风险（车门/行驶中车窗/安全相关） |
| 首次建议 | 卡片（点击应用） | 卡片（点击应用） | 不建议，只语音确认 |
| 已确认过 1-2 次 | TTS 一句话+HUD 轻条（"要开到家放松模式吗"） | 卡片 | 永远不自动 |
| 习得（≥3 次稳定应用） | 计时器确认：通知+15 秒倒计时，不取消即执行 | 计时器确认 | 永远不自动 |
| 长期稳定（≥2 周） | 静默执行+事后告知："到家放松模式已就绪" | 计时器确认 | 永远不自动 |

四个要点：
计时器确认抄奔驰：确认摩擦从"必须点击"降到"不反对即可"——这是卡片之外最重要的形式增量；
静默执行+事后告知是最高信任形态，仅限低风险+长期稳定组合，且事后告知必须可撤销（"撤销本次"则回滚并降一级信任）；
高风险列永远不自动化，这是硬约束，写进验证器不做例外；
信任分级的数据基础恰好是观察入口产生的（应用/拒绝/调整记录）——两个设计互为闭环。
五、对 demo 与 storyboard 的影响
旅程 A（充电等待）、B（宝宝睡着了）保留，呈现形式按第四章矩阵替换：旅程 A 的轻量干预改用 HUD 轻条+TTS（行驶中），旅程 B 停车后用卡片；
旅程 C（分寸的边界）改：删客人模式相关内容，保留拒绝冷却、行驶降级、注入、指标面板；
新增旅程 D（观察入口，本报告核心新增）：周一到周四每晚到家，用户都手动调暗灯光+放轻音乐（demo 快进展示四天）；周五到家，HUD 轻条+卡片"注意到你到家后常调暗灯光听轻音乐，存成『到家放松』场景？"；确认存为个人场景；下周一到家，计时器确认自动执行；两周后静默执行+事后告知。一条旅程演完"观察→建议→习得→无感"完整链路，也是 demo 里最有"车比我懂我"叙事强度的一段；
demo 设置项：入口三选一开关（语音弱意图/观察/全开）+ 呈现形式按信任等级自动切换可视化（面板显示当前每个建议的信任阶段）；
工程上观察入口的 demo 实现成本低：不需要真实行为流，预置"模拟一周操作日志"，模式挖掘用规则脚本，不依赖模型。
六、开放问题（需要你和 fable 一起定的）
模式挖掘放端侧还是云端：端侧隐私好但算力受限（小塔记忆 PRD 的无感记忆提取是 P2，方向可对齐）；云端算力够但行为数据出车需要更强的授权理由。建议 demo 先云端模拟、量产方案端云讨论时再定。
计时器默认执行的允许动作清单：第四章矩阵里"低风险"的划分要以场景引擎的原子能力安全级（注册表 A/B/C 级）为准，第一版建议只放 A 级。
呈现管家窄版的边界：demo 只管场景卡片，还是把观察入口的建议卡也算进同一预算？（我倾向算——两个入口共享打扰度，用户不区分卡片来自哪。）
与运营推荐场景的关系：观察生成的个人场景和运营下发的推荐场景如果撞车（运营推"到家模式"、用户也习惯手动组合），优先级怎么定？（我倾向个人级压运营级。）
