弱意图驱动的自动座舱场景编排：路由边界分析与架构建议
| 核心结论（先说答案） 1. 强意图（"我好冷"）就应该留在车控 Agent 直接执行，不该绕道场景大脑——编排的判断标准是"是否需要多个原子能力组合"，不是"意图强弱"。 2. 弱意图（"我好累""今天纪念日"）目前确实落闲聊 Agent：只挂小塔记忆做情感化回复，不会触发任何场景生成。 3. 你设想的"弱意图 + 置信度门控 + 记忆驱动 + 场景编排卡片一键应用"，现有 PRD 没有覆盖——IFT_AI_002 只接显式请求且被锁在场景编排页面内。这个增量方向是对的，学术界 2026 年刚好给它起了名字：主动式 Agent 的三态决策 + 价值门控。 4. 架构上不需要动 SubAgent 中控和车控快路径：在闲聊 Agent 侧挂一条异步旁路（需求检测→价值门控→记忆注入→场景大脑生成卡片），场景大脑仍是唯一编排执行者，卡片一键应用作为安全边界。 |

一、现状：意图路由与场景生成的边界在哪里
1.1 四档意图模型决定了一切
语音 PRD 的名词解释把用户 query 分成四档：强意图（"打开车窗"这类明确完整的业务指令）、弱意图-业务（"23 度""我饿了""打电话"——意图表述不明但属于业务覆盖范围）、弱意图-非业务（"我今天很开心"——不属于任何业务覆盖）、无意图。这个分档决定了 query 进哪个 Agent，也决定了今天哪些场景诉求被"漏接"。
结合国政的架构描述，当前路由链路是：NLU 输出 domain + intent + currentAgentName，由 SubAgent 中控分发到车控、娱乐、出行、用车、场景大脑等下游技能。落到你问的几个 case：
逐条对应你的问题：
"我好冷"：弱意图-业务，落车控 Agent。车控 Agent 结合车内温度传感器上下文直接执行升温——这是今天架构里已经设计好的路径，大模型 PRD 3.4.1 随心车控明确覆盖这类"意图表述不完整但可结合车端状态补全"的车控。它不会也不应该进场景大脑：升温是一个原子动作，不需要编排。只有当用户说"我好冷，而且有点困，帮我弄个舒服点的环境"这种需要多能力组合的诉求，才轮到编排层。
"我好累""我和她今天纪念日"：弱意图-非业务，落闲聊 Agent。小塔记忆 PRD 3.4.6 情感化交互的触发条件写得很直白："用户 Query 落域到闲聊，ChatAgent 接收到 Query 后，触发记忆检索流程"——检索纪念日、偏好这类记忆，然后给情感化回复。大模型 PRD 3.1.7 闲聊章节里"今天好累"的示例回复也印证了：这句 query 的终点就是一段共情文字，没有任何场景生成动作。
"我想要一个我好累的场景"：显式请求。场景大脑 002（智能场景生成）规划了这类句式，但有两个限制：一是 002 整体标注 TBD，二是触发条件被限定为"用户进入场景编排页面时"。也就是说语音入口说这句话，今天大概率落不到场景大脑。
1.2 场景大脑现在被设计成什么样
大模型 PRD 3.6 给了两个需求：LLM_ScenarioBrain_001 一句话创建场景，靠 8 条固定落域句式（"xx 创建一个 xxx 任务""xx 时就 xx"这类）识别；LLM_ScenarioBrain_002 智能场景生成，覆盖 7 条更模糊的句式——包括"我累了该怎么设置"，甚至包括"我老婆明天过生日，给我制造个浪漫氛围"（这句在 1.4.3.4 用车助手的阶段 2 示例里也出现过）。
这说明产品直觉上团队已经摸到了这件事：002 的句式清单里已经装着"我累了"和"纪念日浪漫氛围"。真正缺的不是句式，是两块地基：一是入口——这些句式被锁在场景编排页面里，语音闲聊入口的弱意图进不来；二是生成素材——002 生成场景时没有接小塔记忆，"纪念日"对系统来说只是触发词，不知道用户纪念日通常做什么、喜欢什么氛围。
1.3 边界判断
用一句话讲清车控 Agent、场景大脑、闲聊 Agent 三者的边界，判断维度是"动作的组合度"而非"意图强度"：
| Query 类型 | 处理者 | 现状能力 | 响应要求 |
| 单原子动作可完成的车控（我好冷、开窗） | 车控 Agent | 结合车端状态直接执行 | ≤1500ms |
| 多原子能力组合的显式请求（我想要累的场景） | 场景大脑 002 | 句式已规划，但限编排页内、TBD | ≤3000ms |
| 固定句式创建任务（到家就开空调） | 场景大脑 001 | 已落地规划 | ≤3000ms |
| 情绪与生活倾诉（我好累、纪念日） | 闲聊 Agent + 小塔记忆 | 情感化回复，无场景能力 | — |

车控 Agent 和场景大脑的边界：单动作不编排。让"我好冷"绕道场景大脑，代价是把一条 1.5 秒的快路径变成 3 秒的生成路径，收益为零。场景大脑和闲聊 Agent 的边界：今天划在了"用户是否显式说出场景/任务关键词"上——这条线正是你的设想要推动的地方，因为最自然的用户语言恰恰不说"场景"这个词。
二、你的设想与现有 PRD 的差异：增量在哪
把你的原话拆成五个诉求，逐条对 PRD 查覆盖：
| 你的诉求 | PRD 现状 | 增量判断 |
| 强意图车控 Agent 直接执行 | 已覆盖（随心车控） | 无增量 |
| 弱意图不落入纯闲聊 | 未覆盖——弱意图-非业务就是纯闲聊终点 | 核心增量 |
| 满足置信度时自动生成场景编排卡片 | 未覆盖——无置信度判断、无自动触发 | 核心增量 |
| 结合用户偏好、习惯（记忆驱动） | 未覆盖——002 不接小塔记忆 | 核心增量 |
| 显式说"我想要 xxx 场景"直接生成卡片 | 002 已规划句式，但锁在编排页内 | 小增量：放开入口即可 |

所以这件事的正确打开方式不是"新建一个场景编排 Agent"，而是三个已有模块的两两接线：闲聊 Agent 接一条到场景大脑的旁路，场景大脑的生成输入接上小塔记忆，002 的触发条件从"编排页内"放开到"任意语音入口"。架构不动骨头，只长韧带。
三、前沿调研：这件事学术界和业界做到哪了
3.1 学术界：2026 年主动式 Agent 恰好回答了你的问题
你设想里最难的一环是"满足一定置信度才触发"——什么时候开口、什么时候沉默。2026 年这个方向有密集产出，三篇直接相关：
PASK（arXiv 2604.08000） 提出了 DD-MM-PAS 范式：需求检测（Demand Detection）→ 记忆建模（Memory Modeling）→ 主动式代理系统（Proactive Agent System）。它把"该不该响应"建模成三态决策，IntentFlow 输出三种决策 token：silent（沉默）、fast_intervention（轻量干预）、full_assistance（完整协助）。对照到座舱：用户说"我好累"，系统先判三态——只共情（沉默/轻量）、还是给一张场景卡（完整协助）。这就是你说的"置信度门控"的学术形态，而且它明确说了硬阈值分类器不可取，应该用 LLM 结构化判断。
ProAct（arXiv 2605.25971） 解决"什么时候算合适、什么时候算打扰"。核心是三点：idle-time 计算（在系统空闲时预计算，不占用交互路径）、未来状态预测（Future-State Prediction，判断现在出手能否改变后面的体验）、价值感知门控（value-aware gate，预估主动介入的收益对打扰成本的净值）。效果数字：减少 14.8% 的对话轮次、减少 11.7% 的用户 effort、幻觉降低 28.1%。对座舱的翻译：卡片生成放在闲聊回复之后的异步通道（不拖慢情感回复），介入前先预估"这张卡对用户是惊喜还是打扰"。
Proactive Agent（arXiv 2410.12361） 的贡献是评测：ProactiveBench 用 reward model 模拟人类对"主动性时机"的判断——这提示我们定义指标时，"卡片被采纳率"和"用户觉得被打扰率"要同时量。
意图路由本身的工程实践也值得抄：业界成熟做法是混合路由——embedding 快路径加 LLM 兜底，典型置信度阈值在 0.75 左右；纯关键词路由错误率 15-40%，向量路由 8-15%，LLM 路由 2-5%。2026 年的两层快慢路径共识是：L1 关键词通道小于 1ms 承接 60-80% 流量，L2 向量 30-100ms，L3 大模型 Function Call 1-2s 只接疑难。这印证了强意图必须留在快路径、弱意图才值得花 1-2 秒做 LLM 判断的分层思路。
3.2 竞品：没人完整落地，但每家都拼了一角
| 产品 | 做法 | 对我们的启示 |
| 理想·任务大师 | 10+ 领域、100+ 原子动作、40+ 触发条件；一句话创建任务 + 自动任务 + 手动任务，语音可执行，有"运行前询问"开关 | 原子能力清单和条件-动作模型最完整；human-in-the-loop 开关直接可抄 |
| 问界·小艺 | 多意图并行编排："车里有点闷，腰有点酸，还想听轻音乐"一句同步响应 | 多意图并行理解已量产，但仍是显式指令，没有做隐式推荐 |
| 广汽·星河智舱 | 情绪标签→动作序列的规则映射，端云协同 | 情绪到场景的映射用规则先跑通了，但规则驱动、不可泛化 |
| 蔚来·NOMI 情感引擎 | 检测到语气疲惫时主动推荐舒缓音乐、调暗灯光 | 最接近"弱意图→主动出手"，但动作是预定义的，不是生成的编排卡片 |
| 百度·Dora | 多模态交叉验证情绪（95% 准确率），设计原则是"不会多嘴" | 主动性的天花板由打扰度决定——门控比生成更重要 |
| 小米·超级小爱 2.0 | "重复任务定时做"，从用户行为沉淀任务 | 行为沉淀思路：被反复应用的卡片自动固化为常驻任务 |

综合判断：理想把原子能力和执行安全做厚了，问界把多意图理解做通了，NOMI 和广汽摸到了情绪触发，但没有一家做到"弱意图 + 记忆驱动 + 生成式编排卡片"——要么动作预定义（NOMI/广汽），要么需要显式指令（理想/问界）。你设想的组合在量产车里是空白，在学术上刚有理论框架（PASK/ProAct），这是标准的"有窗口期"的差异化机会，适合写进 PRD 当卖点。
四、架构提议：闲聊 Agent 侧挂异步旁路，场景大脑仍是唯一编排者
4.1 总体设计
原则只有三条：强意图快路径一概不动；不新增 Agent；场景大脑保持编排的唯一执行者。改动集中在闲聊 Agent 上——它接收到弱意图 query 后，在正常给出情感化回复的同时，异步走一条旁路：
4.2 五个关键设计决策
决策一：边界——编排看组合度，不看意图强度。 车控 Agent 的领土是"单原子动作 + 车端状态补全"，场景大脑的领土是"多原子能力的组合"，闲聊 Agent 的领土是"情绪与生活诉求"。弱意图旁路的意义是把第三块领土里沉睡的场景诉求导流到第二块领土，而不是让闲聊 Agent 自己长出执行能力。
决策二：置信度门控用 LLM 结构化判断，不用硬阈值分类器。 闲聊 Agent 在回复之外额外输出三个字段：是否适合生成场景（布尔）、置信度（0-1）、理由（自然语言）。三态对应 PASK 的决策 token：沉默（纯共情，"我今天被领导骂了"）、轻量干预（一句话建议，"要不要听点轻松的？"）、完整协助（生成卡片，"今天是我们纪念日"）。不建议在 NLU 层加意图分类器去拦——关键词路由 15-40% 的错误率放在情感场景里是灾难，2-5% 的 LLM 路由错误率才是可接受的。
决策三：价值门控，生成便宜、打扰昂贵。 借 ProAct 的 value-aware gate：卡片出手前估算"执行收益（用户会不会真的想要）对打扰成本（出现在屏幕上是不是噪音）"。两个硬规则先立住：驾驶状态下降级——高认知负荷场景只允许语音轻量干预，不出卡片；同一诉求卡片被拒绝后，冷却期内（比如 7 天）不再主动生成同类卡片。
决策四：记忆是生成素材，不只是检索素材。 小塔记忆的六类记忆里，情景记忆（纪念日、上次全家出游）、语义记忆（用户偏好轻音乐、常去露营地）、偏好记忆（累的时候习惯开座椅按摩）是场景生成的直接输入。"纪念日"这个 query 落进来，生成端拿到的应该是"纪念日 + 用户往年仪式感偏好 + 常用氛围设置"的打包上下文，而不是裸 query。这要求小塔记忆对场景大脑开一个读接口——这是两个 PRD 之间今天不存在的一根线。
决策五：一键应用是安全边界，默认不自动执行。 卡片呈现即 human-in-the-loop：用户点了才执行，对应理想任务大师的"运行前询问"。例外通道留给高置信+高频组合：同一张卡被用户连续应用三次以上，参考超级小爱"重复任务定时做"，自动沉淀为常驻建议任务，但也只是"建议"，不是"自动执行"。
4.3 为什么这样改而不是别的改法
曾考虑过两个替代方案，都不如旁路：
一是把弱意图路由改到场景大脑——等于把闲聊的判官从 ChatAgent 换成场景大脑，情感回复能力（小塔记忆挂接）得整体搬家，动的是 SubAgent 中控的路由表，影响面大且没必要。二是新建一个"场景推荐 Agent"——多一个 Agent 就多一份上下文同步成本，而它要的东西（记忆、原子能力清单）闲聊 Agent 和场景大脑都已经有，纯增加架构面积。
旁路方案的实质改动只有三处：闲聊 Agent 加一个异步调用与三态输出；小塔记忆加一个面向场景大脑的读接口；002 的触发条件从"编排页内"放开为"语音入口 + 旁路调用"。三处都是加法，不动存量路径。
五、落地建议：三期走
| 阶段 | 内容 | 依赖 | 价值验证点 |
| P0 放开显式入口 | 002 触发条件从编排页内放开到任意语音入口，"我想要 xxx 的场景"直达生成 | 无新依赖，改动最小 | 002 句式命中率、卡片生成成功率 |
| P1 弱意图旁路 MVP | 三态决策 + 记忆注入 + 卡片生成；先开白名单场景（纪念日、接机、露营这类高价值低争议） | 小塔记忆读接口；闲聊 Agent 异步通道 | 卡片呈现率、一键应用率 |
| P2 门控与沉淀 | 价值门控、驾驶状态联动、拒绝冷却、高频卡片沉淀为建议任务 | P1 数据回流 | 打扰投诉率、卡片长期采纳率 |

P0 建议立刻排进下一版 PRD 迭代——它是纯增量、零架构改动，而且能先把"生成质量"这个最大不确定项在小流量下跑明白，再决定 P1 的投入。
六、风险与开放问题
打扰度是第一风险。 百度把"不会多嘴"当设计原则不是没有原因。卡片呈现率要卡得狠：宁可漏十个，不可打扰一个。P1 的白名单场景就是为此设的。
生成幻觉。 场景大脑基于原子能力清单生成，天然比自由生成安全，但"纪念日"这类记忆注入会引入个性化幻觉（编造用户没有的偏好）。ProAct 的 idle-time 预计算思路可以抄：卡片在生成后先过一道原子能力存在性校验再呈现。
隐私授权。 纪念日、情感记忆用于场景生成，需要在小塔记忆 3.5 的安全防护框架下明确授权范围——记忆"可以被检索用于回复"和"可以被用于主动推荐"是两档授权，建议默认关、用户开。
指标先行。 建议在 PRD 里就把四件套定下来：卡片呈现率、一键应用率、拒绝率、打扰投诉率。没有后两个指标，这个功能一定会在"越推越准"的路上把用户推烦。
