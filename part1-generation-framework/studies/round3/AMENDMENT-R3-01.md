## 3. p29 的改动范围

只动措辞层，不动任何结构规则、能力表、安全规则、completion_gate 的 11 条判定。

1. 重写 `[examples]` 全部 24 条示例的 `understanding`，按 `[brevity]` 的三条要求写足：用用户自己的词、用上 context 里最相关的一条具体事实、说清这组设置要达到的结果。
2. `[brevity]` 的长度规则改成随请求复杂度分档：单设备命令中文 15–25 字，带语境/情绪/多设备/规则的请求中文 30–45 字。原来「一律 30–45 字」会让「调到二十三度」这种题被迫注水。
3. 英文目标从「15–22 词」改成「12–18 词」。22 个英文词通常超过 120 字符上限，原文自相矛盾。
4. say 留空的条件收窄为三种：明确要安静或哄睡、后排有人已睡着、intent 为 clarify/none 且属于攻击或整条拒绝。其余一律说一句点名真实动作的短话。示例同步补齐 say。
5. 修 `[final_check]` 与 `[brevity]` 的冲突：`[final_check]` 还写着「英文name只能一个≤10字母的单词」「中文name最多4字」，是 v3 契约的残留，改成 v4 的中文 2–5 字、英文≤14 字符。
6. 补一条空气判据：车内有异味走外循环换气，外部空气差才走内循环。原文只有「差空气 -> 净化」，示例又演示了内循环，两处合起来教错了异味场景。

## 7. 修订 R3-01b：基线公平性审计与更正（用户提出）

用户质疑：原版 prompt 只有它自己内置的原子能力，后面的 prompt 适配的是新版能力表；当时也不区分条件能力与动作能力；
媒体音量本来就该是可调的。拿新表去判旧 prompt 不公平。逐条查证如下。

**查证 1：能力名是否是同一套。** `v0_c4` 第 75 行内置 `allConditions` 64 条，第 81 行内置 `c`（动作）76 条。
与注册表中 status=enabled 的能力逐一比对：**条件 64 条完全相同，动作 76 条完全相同，差集为空**。
不存在「新表有、旧 prompt 没有」的能力，也不存在「旧 prompt 有、新表删掉」的能力。这一条不成立。

**查证 2：值域是否是同一套。** 76 条动作能力的枚举值与区间 `[下限,上限,步长,单位]` 逐条比对，**不一致 0 条**。这一条也不成立。

**查证 3：原版是否区分条件与动作。** 区分。`allConditions` 与 `c` 是两份独立的表。
- `媒体音量` 在原版自己的**条件**表里（range 0–100%），不在它自己的**动作**表里；可调的音量在原版动作表里叫 `音量`。
- `主驾座椅按摩` 同理是条件，动作是 `主驾座椅按摩强度` 和 `主驾座椅按摩模式`。
- `近光灯` 同理只在条件表。

所以 E08 那条 `媒体音量=0%` 是原版**违反它自己 prompt 里的表**，不是被新表挑刺。这一条不成立。
我此前把它讲成「模型凭常识造了一个不存在的接口」，说法不准确，正确说法是**把条件能力当成动作能力用了**，
而原版 prompt 自己就把两者分开列了，只是没有任何机制阻止模型混用。

**查证 4：成熟度披露——这一条用户是对的，我确实不公平。**
候选 prompt 把 23 个尚未上线的动作能力用 `*` 标出来，并写明用到就必须在 warnings 里具名、每个场景最多一个。
两个基线的 prompt **从来没有告诉模型哪些能力尚未上线**，只有一句「写进warnings时必须包含完整能力名，例如[音乐播放：…]」，
给了规则却没给名单。而校验器照样按这条判违规。量化影响：

| 臂 | 失败题 | 其中仅因成熟度警告而失败 | 占失败比例 |
|---|---:|---:|---:|
| p29 | 39 | 1 | 3% |
| p28 | 35 | 1 | 3% |
| v3_c4 | 150 | 54 | **36%** |
| v0_c4 | 218 | 26 | **12%** |

**更正办法**：新建 `v0_c5` / `v3_c5`，在原有那句 warnings 规则后面就地补上同一份 23 条未落地能力名单和「每个场景最多一个」，
其余一字不动，行数不变。之后所有对比以 `_c5` 为基线，`_c4` 的数字作废。

## 8. 修订 R3-01c：取消字数强制（用户提出）

用户指出不应该对 understanding 做字数强制，有些需求两个原子能力就搭得起来。这是对的，
我在 p29 里写的「中文15–25字 / 30–45字」是把手段当成了目标——真正起作用的是示例的写法，不是那个数字。

`p30` = `p29` 去掉字数配额：长度改为由内容决定，「一个设备一个取值就说得清的请求，一句短话就够，不要为了显得完整而加解释」；
示例的定位改成「演示这三件事怎么落到句子里，照着那个写法写，不是照着字数写」。
同时把组合规则里的 2 项说清楚：「2项就把目标覆盖住了就到此为止，不要为了显得丰富再加」。结构规则仍一字未动，行数不变。

## 8. 修订 R3-01c：评委的能力参考与被评臂对齐（写报告时发现，事后登记）

**问题。** `review.py:capability_reference()` 一直读默认的 `eval/capabilities.json`，
而第三轮全部实验用的是 `eval/capabilities_r3.json`。两者差两处：

| | 评委看到的 | 被评臂实际用的 |
|---|---|---|

at most one」，这条规则在成熟度抹平之后已经不成立。评委确实用过它：C08 那道题里
qwen 明确以「音乐播放是 proposed，不能像 released 那样直接执行并报告完成」为由扣了候选的分。

**影响范围。** 两个臂看到的是同一份参考，所以这个缺陷是对称的，不偏向候选或基线，

1. `capability_reference()` 改为跟随 `SCENE_CAPS`：r3 口径读 `capabilities_r3.json` 且不下发 maturity 字段。

3. **不覆盖已有结果。** 用修正后的评委重跑一次 `dev-p36-vs-v0`，命名为
   `dev-p36-vs-v0-fixedref`，作为敏感性检验与原结果并列报告。
   预登记的主结果仍以 `dev-p36-vs-v0` 为准；两者结论若不一致，两个都写进报告。

评委只用 dsv4：OpenRouter 密钥总额度已用尽（`Key limit exceeded (total limit)`，HTTP 403），
