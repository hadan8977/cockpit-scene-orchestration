# PRD 修改说明与原图处理

## 为什么原稿难懂

这份文档的问题主要来自组织方式和版本一致性。它一边解释产品，一边交代研发架构、实验成绩和历史评审意见。读者还没看完一次完整的用户操作，就遇到大量模块编号和简称；即使读懂某一段，也不确定它描述的是当前 Demo、未来目标，还是尚未同意的建议。

前一轮将评审结论补进正文时，没有把对应旧规则同步清理干净，这也增加了阅读负担。例如，“保存是否隐含自动执行许可，列为待讨论”被加进正文，后面的演示却仍写保存后下周自动执行。给旧规则加一条注释，不能代替形成一致的新规则。

本次按产品、设计和研发同事一起评审方案的用途重写正文。重写是调整阅读顺序、明确现行依据，并完整解释行为；没有修改 Demo 代码，也没有把仍需决策的选择写成已经批准的需求。

## 几处最典型的问题怎样改

### 1 开头先讲产品 不先讲系统中间层

原 1.1 在“能力侧已齐”之后列出场景大脑、场景引擎、小塔记忆和 114 条能力，再说缺少中间一层判断。熟悉项目的人能理解这些名词，第一次阅读的同事却还不知道用户最终会获得什么。

新稿先说明用户能用四种方式获得或保存场景，再用灰尘进入车内的例子解释主动建议的价值。模块和能力交付状态后置。这样读者先理解产品任务，再理解由谁实现。

“能力侧已齐”改为分别说明已交付部分与待接入部分。规划中的记忆、模拟车控和真实车型接口不能归为同一种完成状态。

### 2 将压缩术语展开成具体行为

原文：“边界三件套贯穿全文”“忽略要计费”“谢幕”“新建还是并入”“状态表达旁路”。这些词既有技术含义，也有比喻，读者需要不断翻译。

新稿直接描述：拒绝后结束本次建议；是否长期减少同类建议另有规则；场景结束或撤销时怎样处理设备；什么时候保存新场景、什么时候更新已有场景；用户说出处境后助手怎样正常回应并准备建议。

保留“场景”“触发条件”“偏好”等必要名词。清晰来自指代稳定和解释充分，不靠把所有术语换成口语。

### 3 按最新 Demo 修正范围

原 3.1 和 3.5 写“情绪从不主动”。当前 Demo 的 v20 说明明确增加了心情不好、纪念日建议，仍等待确认；因此新稿不再保留一刀切的禁令，而是说明现有建议入口和需要继续验证的价值边界。

原 2.1 将观察和顺手存全部标为后续。当前 v21 已有预设观察故事、长按快存、保存、自动使用开关和分阶段应用。新稿区分“已有可交互演示”与“真实长期观察学习未完成”，既不漏写新 Demo，也不把预设记录说成真实学习成果。

这些调整依据 Demo 的明确版本说明和线上资源；不能拿更早的 PRD 范围反过来删除当前 Demo 的内容。

### 4 明确同一个 好 在不同入口的含义

原 1.3 将“好”统一解释为应用一次。当前处境建议确实如此，但 v21 的观察建议中，“好”是保存习惯，当前已调好的设置不会重复执行。

新稿用一张简表说明不同入口的现有含义。这是解释当前产品的重要内容，不宜用“采纳”一词笼统带过。

交互上建议将按钮逐步改为能说明后果的用词，例如“应用一次”“保存习惯”。这只是待讨论的文案建议，本次没有修改按钮，也没有声称 Demo 已统一。

### 5 保存与自动使用已有明确交互 不再无限期写待讨论

原 3.4 把两者的授权关系留为 D03。v21 已提供单独的自动使用选择，且明确旧场景不会自动启用。

新稿同步为：保存保留方案，不立即执行；用户主动开启自动使用后，才允许在有效条件满足时触发。这一结论来自当前 Demo，仍需在真实执行服务中验证，不能把前端开关等同于整车链路验收完成。

### 6 不再承诺任何时候都完整恢复

原 3.6 同时出现“按当前值恢复”和“L2 起拍快照”，其他段落又承诺每次都能撤销。读者无法判断用户手动调整后应该恢复什么。

新稿把目标行为写成具体例子：系统调暗后用户又调亮，撤销不能覆盖这次人工调整。非语音演示已有设备接管记录；语音本地路径仍有按值比较恢复，因此在实现状态中保留差异，要求统一验证，没有笼统宣布全部已实现。

### 7 更新真实接口约束 保留尚不能下结论的数字

原 3.4 的“中文 15 字”与当前线上接口不同。2026-09-08 读取的配置中，播报字段上限为中文 30 字符、英文 60 字符。新稿不继续用 15 字限制压缩关键告知内容；这些是模型输出字段限制，也不等于所有 HMI 文案都应使用同一个长度上限。

原文将测试总时延 2.111 秒与“2.5 秒创建到卡片目标未达”连在一起，但两者未必使用同一起止点；报告真正列为未达的是总时延 p95 不超过 2 秒。新稿分别保留数据和目标，并说明完整卡片时限需要端到端测量。

应用率、保存率、撤销率、明确反感和学习正确性分开讨论。原“撤销并降级÷执行”不能覆盖建议阶段的打扰，“提示后保存÷提示”也只能直接说明保存转化，不能单独证明学得正确。

## 九张原图怎样处理

本次附件正文实际包含 9 张流程图，比此前版本多了生成 Agent 架构图。以下按文档中的出现顺序编号，不沿用原待讨论清单里已经错位的“图 5”“图 6”。另外还有一张页眉水印图片，不计入流程图。

| 原图 | 读者需要它回答什么 | 本次处理 |
| --- | --- | --- |
| 1 生成 Agent 架构 | 一句话怎样成为受约束的方案 | 移到技术依据，不作为产品开场；114 条及条件 64、动作 72 的统计按新注册表解释 |
| 2 用户主流程 | 用户说话后怎样看到、修改和使用方案 | 用新稿第一张简图和对应例子承接；保存不应只能画在应用之后，单独保存路径另有说明 |
| 3 语音路由与记忆 | 哪个服务负责识别、回复、生成和执行 | 留给跨团队联调；内部 Agent 名称不混入用户流程 |
| 4 状态表达 A B 方案 | 建议准备与正常答话怎样配合 | 改为技术选型待决，不让用户先选架构；正常回应不等候建议、发声不重叠是应说明的产品结果 |
| 5 观察与顺手存 | 记录如何成为可保存方案 | 按 v21 拆成“保存当前设置”和“保存观察习惯”两段；原图保存后直连引擎容易被读成保存即执行 |
| 6 要不要建议 | 什么情况下值得提出帮助 | 用第 4.1 节说明，区别处境建议、观察习惯和主动快存，不让三类任务共用错误的价值门槛 |
| 7 L0 到 L4 升级 | 学习、提示形式和自动执行怎样变化 | 移入历史设想；当前没有实现这条统一升级轴，不能把它画成首期必经流程 |
| 8 场景生命周期 | 候选、保存内容和本次执行有什么关系 | 用第 4.2 节的操作表解释；保留三者分离的思想，不把它们当作单个对象的互斥阶段 |
| 9 端到端技术链路 | 生成、检查、确认和执行如何对接 | 移到技术依据；去掉作为现行要求的“降至 2.5 秒试演”，离线评测放在发布前而非运行时调用链 |

没有把原图全部重新放回新正文。原来的长横图和窄长竖图缩进 Word 后，文字需要放大才能读清；新正文只保留两张用于理解用户操作的简图，其余信息通过对应规则和技术资料承载。

## 原待讨论项的去向

| 原编号 | 当前处理 |
| --- | --- |
| D01 至少两动作跨类别 | 保留现有处境建议门槛，继续验证；不套到快存和观察保存 |
| D02 通用建议价值 | 保留三组对照，增加持续使用后的反馈 |
| D03 保存与自动触发 | 同步 v21 单独启用的现有交互，补真实执行验证 |
| D04 接管与撤销 | 写清一致的目标行为，显式标出语音与非语音实现差异 |
| D05 合并扩展范围 | 仍需决定和验收；新动作的局部条件不能在合并中丢失 |
| D06 反馈含义 | 正文区分语义，跨入口冷却数值和计数口径待统一 |
| D07 驾驶状态 | 仍需整车可信状态及可交互条件 |
| D08 对话与建议时序 | 先写产品行为，后台并行或串行实现留给联调 |
| D09 固定试演 | 产品保持取消；逐一核对独立执行服务调用，不混为方案自带延时 |
| D10 出厂守护 | 留在后续整车功能讨论，不作为当前主动建议的已交付能力 |
| D11 信任统一升级轴 | 移出主流程，学习、打扰、呈现、自动使用分别说明 |
| D12 两阶段判断 | 作为技术优化方案保留，不为了画图擅自冻结新架构 |

## 本次没有做的决策

没有替团队决定是否取消两个动作门槛、如何扩展情绪建议范围、所有入口统一采用多少天冷却，以及真实车型能执行哪些动作。原文的相关设想和数字保留在依据文件中，方便评审时逐项确认。

本次阅读了附件正文、表格、9 张流程图，以及相关公开版本说明和线上配置。当前环境没有可用浏览器会话，未完成在线点击体验；流程结论依赖所列文档和读取到的代码资源。没有把这次阅读当作端到端交互验收。
